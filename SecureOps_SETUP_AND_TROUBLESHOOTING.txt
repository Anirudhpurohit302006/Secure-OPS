SECUREOPS V1
SETUP, STARTUP, RESTART, TESTING & TROUBLESHOOTING GUIDE
==========================================================

This is the practical guide for running SecureOps on Windows.

ARCHITECTURE
Windows Host -> React/Vite frontend : http://localhost:5173
              -> Java/Spring Boot backend : http://localhost:8080
              -> PostgreSQL 16 : localhost:5432
              -> SSH -> RHEL-01 : 192.168.159.129
              -> SSH -> RHEL-02 : 192.168.159.128

RHEL-01: hostname rhel01, IP 192.168.159.129, SSH user anirudhpurohit
RHEL-02: hostname rhel02, IP 192.168.159.128, SSH user anirudh

==========================================================
3. CONFIGURATION
==========================================================
Create the local environment file:
    copy config\secureops.example.env config\secureops.env
    notepad config\secureops.env

Important values:
    DB_HOST=localhost
    DB_PORT=5432
    DB_NAME=secureops
    DB_USER=secureops
    DB_PASSWORD=<local PostgreSQL application password>
    SSH_PRIVATE_KEY_PATH=C:/Users/ANIRUDH/.ssh/secureops_ed25519
    SSH_PASSWORD=
    SSH_KNOWN_HOSTS_PATH=C:/Users/ANIRUDH/.ssh/known_hosts
    SSH_CONNECT_TIMEOUT_MS=8000
    SSH_COMMAND_TIMEOUT_MS=20000
    ADMIN_USERNAME=admin
    ADMIN_PASSWORD_HASH=<BCrypt hash>
    COLLECTION_INTERVAL_MINUTES=30
    MONITORED_SERVICES=sshd,firewalld,httpd

NEVER commit config\secureops.env.

==========================================================
4. ADMIN PASSWORD / HASH
==========================================================
Generate/change the BCrypt hash:
    Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
    .\scripts\hash-password.ps1

Put the generated hash in config\secureops.env as:
    ADMIN_PASSWORD_HASH=<hash>

Restart the backend after changing it.
The local development username/password is in SecureOps_LOCAL-CREDENTIALS.txt.
DO NOT commit that file.

==========================================================
5. DEBUG ENVIRONMENT LOADING
==========================================================

Useful checks:

15. DIRECT LOGIN API TEST
==========================================================
PowerShell:
    Invoke-RestMethod -Uri "http://localhost:8080/api/auth/login" -Method POST -ContentType "application/json" -Body '{"username":"admin","password":"<YOUR_PASSWORD>"}' | ConvertTo-Json -Depth 10

Successful result:
    {
        "username": "admin"
    }

401 means the backend rejected the credentials.
429 means the login throttle has been triggered.

==========================================================
16. LOGIN TROUBLESHOOTING
==========================================================
If the browser says Invalid username or password:

1. Test the API directly using the command above.
2. Check ADMIN_USERNAME and ADMIN_PASSWORD_HASH.
3. Check the browser DevTools -> Network -> login -> Payload.
4. Username must be exactly:
       admin
   with NO trailing space.
5. Make sure only one backend is running.
6. Restart the backend after changing configuration.

A previous test revealed a trailing space in the browser payload:
    "username": "admin "
That is different from:
    "username": "admin"
and correctly causes a 401.

==========================================================
17. LOGIN THROTTLE / 429
==========================================================
If Invoke-RestMethod returns 429 Too Many Requests:
    - stop repeated login attempts
    - wait for the throttle window, OR
    - restart the development backend

Then test the API once.

==========================================================

3. Check PostgreSQL:

4. Start backend.
5. Start frontend in another terminal.

==========================================================
21. OFFLINE MACHINE TEST
==========================================================
1. Power off one RHEL VM.
2. Wait for collection or use Collect now.
3. Verify it becomes OFFLINE.
4. Verify historical data remains.
5. Verify last successful collection time remains.
6. Power the VM back on.
7. Verify it returns ONLINE after successful collection.

This behavior has been tested successfully.

==========================================================
24. COLLECTION SCHEDULER
==========================================================
Normal interval: 30 minutes
Maximum tolerance: 45 minutes

Targets are collected sequentially:
    RHEL-01 -> collect -> disconnect
    RHEL-02 -> collect -> disconnect

SSH connections are temporary. Historical records are appended.

27. GITHUB / GIT SAFETY
==========================================================
Before pushing:
    git status
    git ls-files

NEVER commit:
    config\secureops.env
    private SSH keys
    database passwords
    real password hashes
    LOCAL-CREDENTIALS.txt
    other secrets

Add this to .gitignore if using the local credentials file:
    LOCAL-CREDENTIALS.txt

Then:
    git status
    git add .
    git status
    git commit -m "SecureOps V1 - PostgreSQL monitoring platform"
    git push

If GitHub detects a secret, STOP and rotate/remove the secret rather than bypassing protection.
